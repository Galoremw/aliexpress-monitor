# 店小秘队列共用监控台 Chrome 与采集机归属设计

**状态：已确认，按设计实施**

**日期：2026-10-30**

## 目标

店小秘采集应在用户已打开监控台的 Chrome 窗口中处理 AliExpress 商品页，并遵守监控台现有“采集电脑”选择。用户选择 QX 电脑后，只允许 QX 领取新的店小秘任务；Galore 主机即使在线，也不能抢走任务。

本次只调整店小秘队列的浏览器窗口和 worker 归属，不清空、重排或自动启动任何队列，不改变商品采集判定、店小秘助手交互、账号角色权限或店铺采集行为。

## 已确认现状

1. `setup-dianxiaomi-worker.bat` 使用独立的 `DianxiaomiProfile`、`--user-data-dir` 和 `--new-window`，因此打开单独 Chrome 窗口及独立扩展环境。
2. `extension/background.js` 的 `ensureDianxiaomiProductTab` 在没有旧窗口时调用 `chrome.windows.create`，也会建立独立商品窗口。
3. 店小秘扩展请求用 `chrome-${chrome.runtime.id}` 作为 worker ID。同一扩展在不同电脑上可能有相同扩展 ID，无法标识 Galore 与 QX。
4. `claim_handoff_batch` 只检查全局暂停状态，未验证领取任务的 worker 是否为监控台当前选定的采集电脑。
5. 日常店铺采集已有稳定的 Chrome profile worker UUID、在线 worker 注册表和 `BrowserCollectionControl.selected_worker_id` 单机选择控制。原先该控制明确不包括店小秘队列。

## 方案比较

### 方案 A：复用监控台现有采集电脑选择（推荐）

店铺采集和店小秘共用同一台被选中的 Chrome worker。所有店小秘领取入口由后端核验该 worker ID；商品页在发起任务的监控台标签所在窗口打开。

优点是只需一个电脑选择，机器归属由服务端强制执行；不会因另一个在线 worker 抢先轮询而切换机器。缺点是店小秘与店铺采集的机器选择不能彼此独立。

### 方案 B：店小秘单独维护采集电脑选择

在店小秘面板加第二个电脑选择器与独立 owner 状态。

优点是两类队列可以使用不同电脑。缺点是界面和状态多一套，容易出现店铺采集选 QX、店小秘仍选 Galore 的混淆。

### 方案 C：只改浏览器窗口，不做服务端 owner 校验

把商品页放进当前 Chrome 窗口，但保留任意 worker 领取任务。

该方案不能解决 QX 任务仍被 Galore 领取的问题，不满足本次目标。

## 推荐设计

### 1. 统一身份和领取权

- 店小秘扩展请求改用现有 `browserCollectionWorkerId` UUID 和 worker label，不再使用扩展 ID 作为电脑身份。
- 复用 `BrowserCollectionControl.selected_worker_id` 作为店铺采集与店小秘采集的唯一选中电脑。监控台“采集电脑”选择器仍是唯一选择入口；店小秘面板展示选中电脑及在线状态。
- 后端店小秘 `claim-next`、`claim-batch`、单条 claim、heartbeat 和状态更新均执行 owner 校验。没有有效 worker ID、未选电脑、非选中电脑或已离线电脑不能领取新任务。状态更新还须确认任务当前归属 worker，防止旧 worker 的晚到回报覆盖新状态。
- 任何保留的服务 token / Docker 领取入口必须受同一归属规则约束，不能绕过 Chrome owner 检查。若无法表达选中 Chrome worker 身份，该入口不再领取此 Chrome 店小秘队列任务。
- 单次只领取一个店小秘任务，继续串行处理。owner 切换只阻止旧 worker 领取新任务；旧 worker 已领取的任务可以完成。旧任务仍有效或租约未过期时，新 worker 等待，不并发领取。租约到期后的重领遵守现有状态恢复规则，并忽略旧 worker 的晚到写入。
- 电脑选择不启动队列。店小秘队列仍由现有继续/暂停控件管理；后端在每次 claim 时检查队列暂停状态及选中电脑。离线不自动切换到另一台电脑。

### 2. 在当前 Chrome 窗口打开商品页

- worker 只在已识别的监控台 worker 标签上下文中轮询队列。
- 建立或复用该监控台标签所在的 `windowId`；商品页以同一窗口中的一个可复用标签打开。不得为店小秘商品任务调用 `chrome.windows.create`。
- 监控台标签保持打开，商品标签可前置供用户完成 AliExpress / 店小秘正常登录和人工验证。商品页身份核验及店小秘助手“本页采集”成功确认逻辑保持现状。
- 将旧的专用 worker 启动流程改为不创建独立 profile、不关闭现有 Chrome 进程、不使用 `--new-window`。正常使用不再需要运行该脚本；用户从已安装两种扩展并已登录的 Chrome 打开监控台即可。

### 3. 状态显示

店小秘面板显示当前选中电脑名称、在线/离线、最后心跳、正在执行该任务的 worker，以及 owner 切换时的等待状态。监控台选择器仍是更改电脑的唯一入口，店小秘面板不增加重复选择器。

## 数据库与兼容性

预期复用已有 worker 表、选中电脑控制记录及店小秘队列控制，不增加数据库迁移。实施阶段如发现字段或持久化约束不足，须先更新本设计再实现。

旧扩展继续使用 `chrome-<extension-id>` 时不能满足 owner 校验，应被后端拒绝领取；扩展重新加载后会通过稳定 worker UUID 重新登记。既有队列项、状态、历史详情和商品数据均保留。发布不自动恢复暂停队列。

## 发布与验收

1. 先部署后端 owner 校验和店小秘状态显示；不重启无关服务，不执行队列清理或数据库迁移（除非实施中证明必要并重新确认）。
2. 将扩展更新并分别在 QX、Galore 当前使用的 Chrome 配置中重载；不再打开独立 DianxiaomiProfile。
3. 让 QX 与 Galore 都打开 worker 模式监控台并在线，选择 QX 后，验证 QX 可以领取而 Galore 的 claim 被后端拒绝。
4. 验证 QX 的 AliExpress 商品页出现在当前监控台 Chrome 的同一窗口；监控台标签仍在该窗口中，任务串行且可正常人工验证。
5. 验证切换电脑时旧任务能够完成或等待租约安全释放；队列暂停时任何 worker 都不能领取。
6. 只有用户手动恢复队列后才进行真实商品页验收；本设计和部署本身不自动开始采集。

## 不在本次范围

- 自动处理 AliExpress 或店小秘验证码、登录或协议确认。
- 同时由多台电脑并行处理店小秘任务。
- 改变店小秘助手判断成功的规则、商品页 ID 校验或采集数据。
- 重置、删除、重新排序或自动恢复现有队列。
- 改动日常店铺采集的页面流程和调度计划。

## 设计审阅自检

- 采集机选择只有一个来源，与已确认意图一致。
- 服务端 owner 校验覆盖领取入口，避免仅靠扩展端自律。
- 同窗行为以监控台标签 `windowId` 为准，不依赖默认 Chrome 窗口或本机 loopback 地址。
- 切换机器、失联、租约到期及旧扩展行为都有明确结果。
- 现有队列不会在部署时被清理或自动启动。
