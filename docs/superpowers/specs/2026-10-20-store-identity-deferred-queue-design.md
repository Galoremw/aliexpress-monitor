# 店铺身份延后审核与队列安全设计

**状态：** 用户已通过
**日期：** 2026-10-20

## 目标

店铺页面身份不明确时，只延后当前店铺任务并继续下一家；不得把未经确认的商品写入监控池，也不得自动认可新 URL。与此同时，避免店铺发现阶段并发领取多家店铺，并在真正的采集失败时停止后续派发。

## 已确认的用户要求

- 身份待核验的店铺在本轮跳过，采集队列继续下一家。
- 人工确认无误只保存该监控店铺对应的 URL 身份；本轮仍保持跳过，不自动补采。用户之后可单独重新排队。
- 人工判定错误时不保存 URL 身份，也不影响队列继续处理其他店铺。
- 登录、验证码等平台验证仍暂停队列，须由用户本人处理。
- 采集故障应停止后续任务派发，修复后由用户手动测试或恢复；不能由修复流程自动恢复队列。
- 不修改监控店铺的规范 ID 或 URL，不根据路由 ID 或店铺名称单独推断身份。

## 当前证据与问题

2026-10-20 队列 #30 的店铺 #6 任务目标 ID 为 `1105161198`，失败信息指出实际页面路由 ID 为 `1105170187`。数据库已有一条属于同一监控店铺的人工批准 URL 身份记录（来源任务 #3196），其历史证据包含页面显示 ID `1105161198`。本次采集仍以通用扩展错误结束，说明后端校验时没有得到足以通过本次校验的身份凭据；现有失败处理没有把这个身份专属问题可靠地转换为可复核的延后任务。

队列检查还观察到同一采集 worker 下同时有两个店铺任务处于 `RUNNING`。店铺发现阶段目前没有严格阻止同一 worker 再领取另一家店铺，这会增加标签页与队列任务错配的风险。

队列 #30 当前为手动暂停状态，且有已领取/陈旧的运行中记录。本设计和后续实现不得自动恢复、重排或改写该运行中的数据。

## 方案

采用现有 `SKIPPED` 终态配合身份专属 `error_type`，不新增数据库状态或迁移：

1. 对扩展预检阶段发现的身份不明确，以及后端处理采集结果时发现的身份校验失败，统一保存当前任务 URL、目标店铺、可用的路由/页面 ID、标题、IXSPY 店铺名和诊断信息，并标记为 `SKIPPED` / `store_identity_deferred`。
2. 延后任务终态化后，队列继续领取下一个店铺。该任务不写商品、销量或店铺快照，不推进该店铺的续页游标，也不自动重试或重新打开当前页面。
3. 监控台提供独立的“身份审核”列表和证据展示，包含待审核、已确认和已拒绝记录，不把延后项算作普通失败。人工确认后保存店铺范围内的 URL 身份记录，任务本轮仍跳过；随后只提供显式“重新排队”操作。拒绝后保留审核结果、不创建身份记录，也不暂停其余队列。
4. 已确认的别名仅在目标店铺相同、规范化 URL 身份精确匹配且没有当前冲突证据时可复用。明确 Store ID 冲突、URL 身份冲突或记录归属其他店铺时仍拒绝并要求人工处理。
5. 店铺发现阶段最多允许一个 `STORE` 任务处于在途状态，即使请求来自同一 worker。产品采集阶段已有的预加载机制不在本次范围内。
6. 非身份类的技术性 `FAILED` 任务触发自动暂停，停止新的领取；合法的部分数据结果不因此暂停。AliExpress 登录/验证码继续使用现有 `NEEDS_VERIFICATION` 暂停状态。

## 数据与状态

- 身份待复核：`status=SKIPPED`、`error_type=store_identity_deferred`，并使用现有 `identity_review_url` 与 `identity_review_evidence` 字段保留证据。
- 人工确认：保留 `SKIPPED`，更新审核结果标记并在 `StoreUrlIdentity` 中保存绑定到目标店铺的身份记录。
- 人工拒绝：保留 `SKIPPED`，设置身份拒绝标记，不新增或覆盖身份记录。
- 人工确认后的显式重排队：只允许该项已经有匹配的、来源为该审核项的批准身份记录时执行；重排队只重置当前店铺项，不重置整批任务。
- 复用已存在的 `SKIPPED` 状态与字段；除非实现中发现数据库约束无法表达上述状态，否则不新增迁移。

## 组件与流程

### 扩展

- 将身份预检结果和后端返回的身份校验错误区分于平台挑战及普通采集失败。
- 提交结构化身份证据；收到延后结果后将当前任务标签页释放到 idle 复用池、释放本地任务状态并轮询下一项，不再重新读取该店铺。
- 不因身份延后而调用平台挑战接口，不再自动停留或反复打开当前店铺页面。

### 后端

- 为预检和采集结果入库两种入口提供一致的身份延后处理，避免身份错误被包装成普通扩展失败。
- 延后单项时原子保存证据并推进队列；失败时原子暂停派发。
- 对店铺阶段领取加入单在途保护；过期租约按现有规则释放，且不在暂停状态下私自开始新任务。
- 人工确认、拒绝和重排队均校验店铺归属、任务状态和 URL 身份，操作幂等且不改写规范店铺 ID。

### 监控台

- 增加“身份审核”过滤项，展示目标店铺、采集 URL、当前证据、延后原因及已完成的人工决定；计数覆盖全部身份审核记录，确保确认后仍可找到单项重排入口。
- 待复核项显示“确定无误”和“错误”；确认后显示“重新排队”，但不自动重排。
- 普通失败与身份延后分开统计；平台验证提示继续独立显示。

## 错误处理与安全边界

- 只有有结构化证据的身份错误可以延后；普通超时、IXSPY 图表故障、无响应、数据库错误不得伪装成身份待核验。
- 缺失的 Store ID 或店铺名称保持缺失，不从标题、路由或别的任务推造证据。
- 未人工确认前，不新增 URL 身份别名、不把候选商品加入监控池、不更新销量。
- 同一个 worker 不得在店铺发现阶段持有两家 `RUNNING` 店铺任务；新版本不得尝试接管旧 worker 或旧 claim。
- 队列手动暂停或自动暂停后，不因心跳、浏览器重载、身份确认或部署而自动恢复派发。
- 手动审核和重新排队操作针对单个店铺项，不能改变其他店铺、产品池或历史采集记录。

## 测试与验收

### 后端

- 身份预检异常与入库阶段 URL/Store ID 校验异常都转为延后项，保留可用证据且不保存商品数据。
- 延后项成为终态后，队列可以领取下一家；延后项不阻挡整批完成。
- 普通技术失败会暂停派发；部分数据按现有业务规则记录，不被误当作技术失败。
- 同一队列店铺发现阶段第二次 claim 不会产生另一条并行 `RUNNING` 店铺项；产品预加载行为不回归。
- 确认只记录同店铺身份且不恢复队列；拒绝不建别名；确认后重排只影响单项。
- 当前冲突 ID、跨店铺 URL 归属、陈旧任务和重复请求均安全处理。

### 扩展与监控台

- 身份延后后当前标签页被释放，下一店铺可继续领取，当前任务不会被循环重开。
- AliExpress 挑战仍暂停并保持人工验证页面；普通采集失败不会被当作身份延后。
- 仪表板将延后项独立呈现，不混入失败数；确认后只显示手动重排入口。

### 生产验证（单独授权）

先在当前暂停队列中只重排一个可控的身份问题店铺，确认身份异常会跳过并继续下一店；再确认普通采集故障会停派；最后人工确认一个延后项并检查 URL 身份跨电脑共享，之后手动重排该店铺。不得以单元测试、worker 心跳或扩展版本号替代真实页面采集验收。

## 不在范围内

- 自动接受 URL 路由 ID 变化或自动更改规范店铺 ID。
- 自动跳过 AliExpress 登录/验证码。
- 自动把未核验商品或销量写入监控池。
- 自动重试身份不明任务，或自动恢复当前暂停的 #30。
- 重启 backend、修改生产队列、重载扩展或在第二台电脑上替用户完成验证。
